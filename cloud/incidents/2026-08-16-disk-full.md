# Incident: cloud.amux.io down — host root disk full (2026-08-16)

**Status:** unresolved at time of writing (awaiting a boot-disk resize, owner action).
**Severity:** SEV-1, full customer-facing outage of cloud.amux.io.
**Tracking:** AC-361 (outage), AC-362 (owner-alert paged nobody), AC-365/AC-366 (the E2E prevention).

## Summary

cloud.amux.io returned 502 on every endpoint for hours. The cloud host's root disk
(49G) is 100% full, so the gateway service could not start (systemd `activating`,
28 restart attempts) and a deploy could not write. The disk is full of legitimate
data, not junk: 32G of it is per-workspace docker volumes across 67 provisioned
workspaces. There is nothing to safely reclaim; the fix is a larger disk.

The outage was invisible until a routine freshness tick happened to probe the site.
Nothing alarmed on host disk, the failed deploy read as an ordinary deploy failure,
and when the owner-alert was fired it reached zero channels.

## Timeline (UTC)

- **08-15 23:12** — deploy-cloud run `31914150334` on `73fce92` succeeds. This is the
  last good image; the host is already close to full.
- **08-16 ~11:30** — deploy-cloud run `31944513119` on `6ebef13` fails at the **deploy**
  job (build passed) with `grep: write error: No space left on device` and
  `rsync: write failed ... No space left on device (28)`, exit 11. First hard signal,
  but it reads as a deploy failure, not a host-health failure.
- **08-16 ~11:30 onward** — the gateway cannot come up on a full disk; cloud.amux.io
  serves 502. No alarm fires.
- **08-16 (freshness tick)** — the every-6h cloud freshness tick probes the site, finds
  502 and `behind=28`, and the investigation begins. SSH to the host initially times out
  (login wedged by the full disk); it later becomes reachable.
- **08-16** — root cause confirmed: `/dev/root 49G 49G 0 100% /`. `amux alert` fired and
  reached **no channel** (email token `invalid_grant`, 0 push subs, `AMUX_OWNER_PHONE`
  empty). Owner reached instead via a direct Gmail send and the board.
- **08-16** — safe reclaim performed (logs): ~278M freed, `docker image prune -f` finds
  0 dangling images. Insufficient. Escalated with a single ask: resize the disk.

## Root cause

The host is undersized for its own steady state. Breakdown of the 49G root disk:

| path | size | what it is |
|---|---|---|
| `/var/lib/docker/volumes` | **32G** | per-workspace persistent data (customer data), 67 workspaces |
| `/var/lib/docker/overlay2` | ~16G | image + container writable layers |
| `/var/lib/docker/containers` | 172M | container json-logs |
| `/var/lib/docker/image` | 60K | image metadata |

67 workspaces have accumulated with no per-workspace quota and no reaping of stopped or
abandoned ones. Volume data grows monotonically. On a fixed 49G disk that reaches 100%
with certainty; the only question was when. `docker image prune` reclaimed 0B precisely
because the space is data and in-use layers, not junk.

## Why it was invisible

1. **No host-disk alarm.** Nothing watched disk usage, so a slow fill crossed 100% with
   no warning. The first symptom was a total outage.
2. **A failed deploy reads as a deploy failure, not a host failure.** The
   `No space left on device` error was in the deploy job log, not surfaced as host
   health. (Related: AC-344, deploy-cloud SKIP is silent.)
3. **The owner-alert reached nobody.** All three channels were down at once (AC-362):
   the alert email path picked a stale-token account, push had no subscriptions, and no
   phone was configured. The one path meant to page in an emergency was silently dead.
4. **No end-to-end test exercises the live product as a user.** Nothing signs in and
   loads a customer environment on a schedule, so "the whole site is 502" was not caught
   by any check. This is the gap the E2E work (AC-365/366) closes.

## Remediation

- **Now (owner, GCP):** resize the boot disk from 49G to 120-200G; the filesystem grows
  on reboot. Then re-run deploy-cloud (image is 28 commits behind) and verify recovery.
- Safe host-side reclaim was already done (logs) and is not enough; the remaining space
  is customer volumes and in-use layers, so no agent-side cleanup can fix it without
  risking customer data.

## Prevention (each item is a follow-up)

1. **Host-disk alarm** at >85% that surfaces in amux health and pages before the disk
   fills. This is the "make the next occurrence self-announce" fix; a disk-full should
   never again be discovered by a 502.
2. **Per-workspace volume quota + reaping** of stopped/abandoned workspaces, so 67 (and
   growing) workspaces cannot fill the host unbounded.
3. **Surface `No space left on device` in deploy-cloud as host health**, not only as a
   deploy failure, so the freeze is legible.
4. **Fix owner-alert paging (AC-362).** amux fixed the email channel to auto-select a
   live account (`c548a40`); push subscription and `AMUX_OWNER_PHONE` remain owner setup.
5. **End-to-end tests per customer environment and persona (AC-365/366)** that sign in as
   a user, load each environment, and exercise each worker. A scheduled run of these
   would have gone red the moment the gateway 502'd. This incident is the argument for
   them.

## What went right

- The freshness tick's own probe (recently hardened, AC-360) surfaced the outage.
- The `/api/email/send` Gmail path (distinct credential from the alert path) provided a
  working escalation channel when the fire-alarm failed.
- Diagnosis reached the exact root cause (disk breakdown, 32G volumes) rather than
  guessing, so the remediation ask is a single unambiguous action.
