## Database Schema Migration: Python→Rust Compatibility

**Issue:** During Python→Rust migration, the `last_verified_at` column in the board table was stored as **TEXT** in the actual database, while the schema definition expects **INTEGER**.

**Symptom:** Orchestrator crashes on startup with:
```
Invalid column type Text at index: 24
```

**Root Cause:** Python server may have created this column as TEXT despite schema definition, leaving legacy data incompatible with Rust type expectations.

**Fix:** Read `last_verified_at` as `Option<String>`, parse to `i64`, with fallback to NULL for unparseable values. This maintains backward compatibility while supporting the new schema.

**Code:**
```rust
// Before: last_verified_at: r.get(24)?,
// After: Read as Option<String>, parse to i64, handle null/empty
last_verified_at: r.get::<_, Option<String>>(24)?
    .and_then(|s| s.trim().parse::<i64>().ok()),
```

**Impact:**
- ✅ Orchestrator no longer crashes on startup
- ✅ Backward compatible (handles both TEXT and INTEGER values)
- ✅ Preserves Python server compatibility
- ✅ No schema changes needed
- ✅ Works for any deployment that migrated from Python

**Affected Deployments:**
Any amux instance that:
1. Previously ran the Python server
2. Created database tables via Python
3. Now runs Rust server

This fix is essential for migrations from Python→Rust.
